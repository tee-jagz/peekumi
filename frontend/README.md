# Frontend

On a phone, you use the browser interface to explore the repository structure, compare commits, follow dependencies and inspect source. The interface uses JavaScript, HTML and CSS to show the SVG map and the glass review panel.

- `app.js`: the map, API requests, revision controls, the review panel and the dock. It draws the view on top of the stack (`nav.js`).
- `nav.js`: the view stack. A view is a plain value: the map in one aspect (Details, Source, Changes or Relations), Ask, Conversations, Tasks, History, the task form, the instructions on a selection, or a run. Opening a view pushes it; Back, Escape and a page's back arrow pop one. No other module keeps navigation state.
- `ask.js`: conversations for a specific scope, which show each question immediately, and explicit actions that change a suggestion into a draft.
- `workflow.js`: instructions (stored as comments), task preparation, run progress, agent evidence and verification, and the live line on the sheet's title row that leads to an agent at work or an open session.
- `model.js`: the directory hierarchy, the aggregation of dependencies and the filter for symbol diffs.
- `icons.js`: original SVG icons with rounded strokes. Object types, Git status, input/output indicators and icon-only controls share these icons. Control glyphs are decorative. Each button has its own accessible name and tooltip.
- `canvas.js`: SVG pan, pinch, zoom and card positions. The visible map is the part above the floating controls and the sheet. The first view, Fit and centering use that part, and a pan stops while some cards are still in view. Until you move the map, a new size (the sheet, a turned phone) places it again.
- `fixes.js`: the Proposed fixes page. It shows the server's fixes for the rule breaks at the map's commit. The owner selects, edits and clears fixes, then saves them as draft instructions or sends them together to the task form.
- `pwa.js`: the installable app shell. Offline and an update are quiet notes in the header's comparison row, never a card.
- `select.js`: frosted menus that replace native select popups. Each `<select>` stays in the DOM as the source of the value and of the change event. A button and a listbox copy its state, and they accept the arrow, Home/End, Enter and Escape keys.
- `text.js`: a safe Markdown renderer (paragraphs, lists, code, bold, italic) for answers, instructions and agent reports. It builds DOM nodes and never parses HTML. When the server resolved a code span, that code span becomes a link into the map.
- `peek.js`: Peek, the mascot, as an inline SVG. CSS animates its state (idle, loading, thinking, success, error, empty). Peek is decorative, and it stays still when reduced motion is on.
- `menu.js`: the context menu. A long press, a right-click or the context-menu key opens a small menu of actions for a map card or a name in a conversation; `app.js` decides which actions fit.
- `focus.js`: the agent focus on the map, for a session, a running task and an Ask answer. It marks the agent's current place, its trail and the changed files, moves the map with the agent (Follow) and puts its card in the middle.
- `session.js`: the Session view and composer. It reads a session's agent log into a conversation of messages, steps and their output for Claude Code, Codex and Peekumi's own agent. It also shows the agent's command requests and the way to end a session.
- `agents.js`: the Agents sheet. It shows the agents, models and efforts that the server lists for Ask and for tasks, and keeps the choice on the device for each repository. Each Ask question, task preview and commit message request sends the choice as `using`, and the server checks it.
- `index.html` and `style.css`: the page structure and the responsive appearance.

The phone sheet expands from a compact selection summary to half height or full height. You can use pointer controls or keyboard controls to do this. Details, Source, Changes and Relations are direct views of the map. Other pages (Conversations, Ask, a session, Tasks, a task) open over them with one header row. The dock at the bottom follows the view: Ask, Instruction and Session modes on the map, and a conversation's own box elsewhere. When a phone keyboard opens, the dock follows the visual viewport. The navigation surface is always one SVG graph, and commit mini cards appear only in Time mode.

The review sheet is frosted glass over the background gradient. Its buttons, tabs, rows and inputs are also frosted. Text inputs are more opaque, so that their text is easy to read. Native select popups follow the browser.

The frontend shows committed documentation as plain text. It does not execute code from inspected repositories. When you build the backend, the backend embeds these assets.

The sheet follows the pointer movement continuously. When you release the pointer, the sheet animates to a snap height. When reduced-motion settings are on, the sheet does not animate as it settles. A change of height keeps the graph DOM and its transform. On a phone, the map keeps its size while the sheet moves over it, and the map changes size one time when the sheet settles. Thus, a drag does not calculate the layout of the SVG map again in each frame.

Only top-level glass surfaces use backdrop blur. Elements in a frosted surface use translucent tints. The canvas Legend explains the Git colours and the line styles for static relationships. Its text agrees with the active colour lens.

By default, Time and Diff both follow the first parent of the selected commit. This default does not depend on the base that you set at launch. When you select a base, that base stays fixed while you change heads, refresh or change modes. The automatic option in the revision picker clears that override. “Use previous commit” also clears it. When you explicitly inspect an instruction or a run, the inspection keeps the comparison range that it requested.

The compact phone sheet shows the selection description and the available input/output types. It does not show inspection controls. Inputs, outputs and fields are lines of name/type tokens that scroll sideways. These lines show only declared types. An Out row appears only for a declared return type or description. At half height and full height, the sheet shows navigation and the complete declaration details, and each absent annotation has an explicit label.

The map key is in the floating canvas toolbar. It opens upward over the graph and contains the Structure/Changes colour lens.

Selection status, review lists and the legend use coloured SVG icons with different shapes. These icons have no badge borders or backgrounds. For inputs and outputs, the contract uses an arrow that goes in and an arrow that goes out. Icons have accessible names and tooltips, and the canvas legend explains them. Modified items use orange in the two themes.

Tasks is an icon button in the header. Thus, the task state shows in each view without a badge. While an agent runs, Peek works in place of the icon, and a small Peek with one word at the right of the sheet's title row opens that task. The button always opens the Tasks list. When the agent finishes, Peek hops one time, and the icon comes back in the accent colour to show a ready task. A task that stopped before the end, with its instructions open, shows a Peek that droops on a warm tint until you handle it. The accessible label and the tooltip tell which state applies.

The task view shows the same Peek next to its heading, and this Peek stays steady when the poll draws the view again. One task view contains the draft selection, a readable task preview, agent updates, results and review. Raw event streams and generated prompts are diagnostics. Unified diffs show the line numbers before and after, and they hide Git transport headers. A review records only the owner verification, and the interface explicitly shows that this is different from an application or a deployment of changes. Git ancestry tells if the task commits are applied to the watched branch, but Peekumi does not infer deployment from that status.

The line below the header title shows the viewed branch and the base → head comparison. This line opens the comparison popover, which contains the branch picker, the head and base selectors, Use previous commit and refresh. The branch picker inspects local refs and remote-tracking refs that are already fetched. It does not check out or fetch branches. History follows the selected branch, and the URL keeps the selection after a reload.

Completed tasks offer Explore changes. This action opens a comparison of the agent branch with the commit where the task started, and it shows a Back to task chip. Tasks shows its ready cue until you review the task. Dispatch still goes to the configured watched branch, and the task preview identifies this branch.

Dependency lines leave and arrive through the top edge or the bottom edge of a card, and each line has its own port. Each line ends with a straight segment that is longer than the arrowhead, so the line meets the chevron along its axis. The chevron has one size for all line widths. If a line would cross another card, the line goes around that card through the row gaps and the nearest gap between columns. Lines that go around to the same card merge into one trunk with one arrowhead.

Every level (repository, folder and file) uses the same compact grid. Space opens only where a line needs it, and only in the column of that card. A gap becomes larger when a line turns through it, so the space around each column is independent. The gap between columns becomes wider when neighbours in a row have a connection. The arrow goes from the middle of the side of one card to the middle of the side of the other card. If the two cards are level, the arrow is straight. If one card is lower, the arrow makes an S in the gap between them, so it does not touch a card. The cards do not move to make the arrow straight.

When you select a card, Peekumi highlights the connections of that card by direction: accent for what it uses, teal for what uses it. It also fades unrelated lines and cards. If the selection has no connections, nothing fades. A modified declaration names the parts that changed: signature, documentation or implementation. Small icons on its card show these parts, and words show them in the sheet, Details and the Changes list.

Map cards use one neutral object-type icon next to the name, and this icon comes from adapter metadata. Folders, file groups, files/modules, classes/structs, functions/methods, interfaces/traits and enums have different icon families. Accessible names and tooltips continue to give the exact types. The card tint shows the Git status, and card titles and filename previews do not show redundant status dots. Descriptions, counts and symbol-change previews stay complete.

The chrome is minimal, so the map keeps most of the phone screen. The header contains the repository name, the comparison line, the Time/Diff icons and Tasks. On the map, Before/After floats in the top-left corner. Home and Up float in the bottom-left corner, next to the Changes only, zoom, fit, reset and key controls. All these controls have the same compact frosted shape. Peekumi announces the current level to assistive technology and names it in the sheet.

Directory cards show a summary of the added, modified and removed counts and the file total, not truncated chips with child names. The accessible name of the card includes these counts. Inspection views, Ask/Instruction, send, save and cancel are icon buttons. The active inspection view also shows its label. A popover closes when you push Escape, push its close button or press the pointer at a different location.

At peek height, the sheet shows complete text. A long summary or input/output list scrolls by whole lines, and its last line fades while more text is available. Lists and notices in the sheet use the same frost, but code, diffs and text inputs are more opaque. Tasks, instructions, conversations and the merge step are plain rows under hairlines, with no card, tint or shadow; a task's title is its first instruction, and only its next step is a primary button. Popovers and select menus use a denser glass, so the map does not show through them. The size of the map key agrees with the space above the floating toolbar.

Three shared primitives make the review sheet: frosted section cards (`section()` in `app.js`), list cards and a code box. Each row of a list card shows a status icon, a title, a muted detail and a chevron. Inspection tabs are outside the content that scrolls. When you choose a view, a sheet at peek height goes up, but a sheet at half height or full height never goes down. In Source, the header stays in its position, and the code box fills the height that is left in the sheet. The code box scrolls inside itself.

Details shows the facts of the selection (kind, counts, path, analysis) with one clear action. Relations rows read `from → to` with the kind, the status and the before/after counts, and they have no code-styled badges. File cards use icons for source, documentation, data/configuration, image, binary/restricted and other files. Files that an adapter parses are source, and the other files follow their extension.

The workflow poll draws again only when the task data changed and a task view is open. Thus, Source and Details keep their scroll position during agent runs. The open view of the panel is `data-view`. Only the tab buttons use `data-tab`.

You can also use the comparison menu to select registered local repositories. A switch shows the branch controls or the GitHub PRs. A PR opens as a merge-base comparison, and the sheet shows the details of the PR. A long frosted list (more than 12 entries) has a filter box and opens at its current entry. When you change the repository, the app loads again to isolate the source state and the workflow state. The installable PWA caches only the assets in the explicit app-shell allowlist. Its service worker never caches API data or source.

A frosted card with Peek tells you about a new version, with Later or Reload. If a box contains unsent text, Reload first tells you that it will clear that text. It also tells you that the saved Ask conversation and instructions will stay. When the app is offline, it uses the same card. Read-only devices have restrictions that the server enforces, and they have no agent composer.

The server embeds each frontend file and serves it by name, and the service worker caches the same list. When you add a file, add it to the static files in `backend/main.rs` and to `SHELL` in `sw.js`. A Rust test checks both lists.
